# Distribution — how hushlog reaches a machine

This is the operator's guide: what to set up once, and what happens on every
release. Read it top to bottom the first time; after that, the
[Release checklist](#release-checklist) is all you need.

The goal of this document is the one line in the README: **a stranger on a fresh
machine runs one command and gets a working `hushlog`.**

---

## 1. The channels

| Channel | Command a user runs | Set up by | Secret it needs |
|---|---|---|---|
| Shell installer | `curl -LsSf https://github.com/adenijiridwan43/Hushlog/releases/latest/download/hushlog-installer.sh \| sh` | cargo-dist | none |
| PowerShell installer | `irm https://github.com/adenijiridwan43/Hushlog/releases/latest/download/hushlog-installer.ps1 \| iex` | cargo-dist | none |
| Homebrew | `brew install adenijiridwan43/tap/hushlog` | cargo-dist + tap repo | `HOMEBREW_TAP_TOKEN` |
| crates.io | `cargo install hushlog` | `.github/workflows/publish-extra.yml` | `CARGO_REGISTRY_TOKEN` |
| Container | `docker run ghcr.io/adenijiridwan43/hushlog` | `.github/workflows/publish-extra.yml` | none (uses `GITHUB_TOKEN`) |
| GitHub Release | download an archive | cargo-dist | none |

`release.yml` is **generated by cargo-dist** and must never be edited by hand:
`dist plan` fails with "out of date contents" if it is. Jobs cargo-dist cannot
model (crates.io, Docker) live in `publish-extra.yml`, triggered when the release
is published.

## 2. One-time setup

### 2.1 crates.io token

1. Sign in at <https://crates.io> with GitHub.
2. Visit <https://crates.io/settings/tokens> → **New Token**.
3. Name it `hushlog-github-actions`, scope **publish-update** (not
   `publish-new`; the crates already exist after the first release, so
   update scope is what re-publishing needs — use **publish-new** for the very
   first publish of each crate).
4. In the GitHub repo: **Settings → Secrets and variables → Actions → New
   repository secret** → name `CARGO_REGISTRY_TOKEN`, value the token.

The first release needs the token to have **publish-new** for all four crates.
After that, rotate it to **publish-update**.

> The crates must be published in this order, which `publish-extra.yml` handles:
> `hushlog-core` → `hushlog-rules` and `hushlog-render` → `hushlog`. crates.io
> rejects a crate whose dependencies are not yet live.

### 2.2 Homebrew tap

1. Create a **public** repository named exactly `homebrew-tap` under your
   account: **github.com/new** → owner `adenijiridwan43`, name `homebrew-tap`,
   public, initialise with a README.
2. The repository must contain a `Formula/` directory. Create it with a
   placeholder file so the first push has somewhere to land:
   `Formula/.gitkeep`.
3. Create a token that can write to that tap:
   - **Fine-grained token** (recommended): <https://github.com/settings/tokens?type=beta>
     → **Generate new token** → repository access: only `homebrew-tap` →
     permissions: **Contents: Read and write**.
   - **Classic token**: <https://github.com/settings/tokens> → scope `repo`.
4. In the **hushlog** repo: **Settings → Secrets and variables → Actions → New
   repository secret** → name `HOMEBREW_TAP_TOKEN`, value that token.

The tap name is declared in `Cargo.toml`:
```toml
[workspace.metadata.dist]
tap = "adenijiridwan43/homebrew-tap"
```
If the tap repository does not exist, the `publish-homebrew-formula` job fails
loudly — it does not silently skip. The other channels still ship.

### 2.3 Container registry

Nothing to do. `publish-docker` uses the workflow's own `GITHUB_TOKEN` with
`packages: write`, and pushes to `ghcr.io/adenijiridwan43/hushlog`. After the
first release, set the package's visibility to public under
**Profile → Packages → hushlog → Package settings**.

## 3. What a release does

Pushing a tag matching `v*` starts `release.yml`:

```
plan ─► build-local-artifacts (5 targets) ─► build-global-artifacts ─► host
                                                                        │
                                    ┌───────────────────────────────────┤
                                    ▼                                   ▼
                         publish-homebrew-formula            (GitHub Release created)
                                                                            │
                                                          release: published ▼
                                     publish-extra.yml ──► publish-crates + publish-docker
```

Targets built (from `Cargo.toml`):

| Target | Runs on |
|---|---|
| `x86_64-unknown-linux-musl` | Linux x64 (static) |
| `aarch64-unknown-linux-musl` | Linux arm64 (static) |
| `x86_64-apple-darwin` | macOS Intel |
| `aarch64-apple-darwin` | macOS Apple silicon |
| `x86_64-pc-windows-msvc` | Windows x64 |

Each archive ships with a `.sha256` checksum. `publish-prereleases = true` means
an alpha like `v0.1.0-alpha.1` also publishes to the tap and the registry, so the
whole chain can be smoke-tested before the first stable tag.

## 4. Release checklist

Run through this once, in order, on the release machine.

- [ ] `cargo fmt --all --check` is clean
- [ ] `cargo clippy --workspace --all-targets -- -D warnings` is clean
- [ ] `cargo test --workspace --all-targets` is green
- [ ] `dist plan` exits 0 (the generated `release.yml` is not stale)
- [ ] `cargo package -p hushlog-rules --list` still shows all 11 rule packs
- [ ] `CHANGELOG.md` has an entry for the version, moved out of `[Unreleased]`
- [ ] The workspace `version` in `Cargo.toml` is the version being tagged
- [ ] `README.md` install section matches reality
- [ ] Tag and push: `git tag v0.1.0-alpha.1 && git push origin v0.1.0-alpha.1`
- [ ] Watch the `Release` workflow go green
- [ ] Watch the `Publish extra channels` workflow go green
- [ ] Smoke-test each channel from [section 1](#1-the-channels)

### Verify an install

```sh
# Shell installer (Linux/macOS)
curl -LsSf https://github.com/adenijiridwan43/Hushlog/releases/latest/download/hushlog-installer.sh | sh
hushlog --version

# PowerShell (Windows)
irm https://github.com/adenijiridwan43/Hushlog/releases/latest/download/hushlog-installer.ps1 | iex
hushlog --version

# crates.io
cargo install hushlog
hushlog --version

# Homebrew
brew install adenijiridwan43/tap/hushlog
hushlog --version

# Container
echo "error: example" | docker run --rm -i ghcr.io/adenijiridwan43/hushlog --format plain
```

Every one must print `hushlog 0.1.0-alpha.1`.

## 5. Windows notes

Windows is a first-class target (`AGENTS.md` section 8).

- The PowerShell installer is the native path; `cargo install hushlog` also
  works if the MSVC toolchain is present.
- Pipes are the default. `--pty` is opt-in and needs a real console; it is not
  intended for CI runners.
- A child terminated by a signal reports exit code 128 (distinct from a genuine
  exit 1). See the CHANGELOG entry for the `ExitStatus::code()` fix.

## 6. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `dist plan` says "out of date contents" | `release.yml` was hand-edited | `dist init --yes` to regenerate |
| `publish-crates` skipped | `CARGO_REGISTRY_TOKEN` unset | add the secret (§2.1) |
| `cargo publish` fails "already uploaded" | version exists on crates.io | expected; the job skips it already. Bump the version |
| `cargo publish` fails "dependency not found" | library crate not live yet | ensure `publish-crates` order is core → rules/render → hushlog, and let the `sleep` run |
| `publish-homebrew-formula` fails on checkout | tap repo missing or token lacks write | create the tap and re-issue the token (§2.2) |
| Docker push denied | package visibility or `packages: write` missing | check the job's `permissions` block |
| Installer 404 | the tag's workflow has not finished | wait for `Release` to go green, then retry |
